# AI SRE — Kubernetes Incident Debugging System (MVP)

Multi-agent система, която разследва Kubernetes инцидент и обяснява причината.

**Състояние: chunk 6.** Веригата е минавала end-to-end през **разположения**
workflow девет пъти; записите са в `docs/runs/`.

Колко е готово се чете от артефакти, не от този абзац:

```
node scripts/readiness.mjs --short
```

Числото има три състояния, не две — зелено, червено и **неустановено** — защото
да броиш неустановеното за провал прави проект, който още не е питан, да
изглежда счупен, а да го изхвърлиш прави проект, който не може да отговори, да
изглежда завършен.

## Какво прави

```
Fake Datadog alert
  → n8n
  → Kubernetes Agent ─┐
  → Logs Agent       ─┼→ Root Cause Agent → Fake Slack thread → Incident Chat
  → Metrics Agent    ─┘
```

Всичко външно е симулирано: няма реален Datadog, Kubernetes или Slack.
MVP-то е **read-only** — агентите препоръчват действия, не ги изпълняват.

## Къде какво стои

| Папка | Какво |
|---|---|
| `schemas/` | каноничният incident обект и всичко около него, като JSON Schema |
| `scenarios/` | fixture данните на сценариите; `registry.json` държи номерата |
| `prompts/` | prompt-овете на агентите, version-controlled |
| `src/` | детерминистичното ядро — providers, scoring, correlation |
| `tests/` | сценарийни и integration тестове |
| `workflows/` | export копия на n8n workflow-ите |
| `docs/` | архитектура, incident модел, симулация, n8n, бъдеща production схема |

## Как се работи

`CLAUDE.md` е правилата. `PROGRESS.md` е дневникът — номерът на текущия кръг
се чете оттам, не се помни.

## Как се проверява

```bash
npx vitest run                     # работи ли кодът
npx tsc --noEmit                   # стягат ли типовете
node scripts/acceptance-gate.mjs   # направено ли е обещаното
```

Първите два и третият отговарят на **различни** въпроси. Тестовете казват дали
кодът работи. Gate-ът казва дали обещаното е построено — а тест, който никой не
е написал, не пада, просто го няма, и всичко изглежда зелено.

Gate-ът има четири изходни кода и третото състояние не е учтивост:

| Код | Какво значи |
|---|---|
| `0` | всичко е проверено и всичко минава |
| `1` | нещо се провали, а всичко останало е установено |
| `2` | нищо не се е провалило, но нещо **не можа да се установи** |
| `3` | и провал, и неустановено |

Gate-ът държи два списъка и ги печата на всяко пускане:

* **не може да реши никога** — минал ли е diff-ът през преглед, писана ли е
  памет. Печатат се, не влияят на кода: проверка, която не може да бъде
  удовлетворена, учи хората да пренебрегват числото.
* **може, но още не е написано** — днес: точките от Definition of Done, чието
  доказателство е отговор на модел. Всяко носи условие, при което започва да
  държи `2`. Маха се, като се напише проверката, не като се изтрие редът.

Една от проверките заслужава отделна дума: **мутационната**. Тя връща в кода
записан дефект — по един, един по един — пуска тестовете и иска именуваният за
него тест да падне. Ако не падне, тестът е украшение и gate-ът го казва.

Файлът се възстановява с обратна редакция, никога с `git restore`: git би
изхвърлил и всяка друга незаписана работа в същия файл.

Това е механизмът зад правилото „всяка поправка носи тест, който пада без нея".
Дотогава то беше твърдение, което нищо не проверяваше — а точно това е дефектът,
който проектът лови навсякъде другаде.
